- purpose: iOS peer of the desktop duocb clipboard-sharing app. Each installation holds its own application keypair (nsec) and a signed, expiring identity card naming `<short-name>_<permanent-suffix>`; trust is a local list of imported peer cards, not a shared secret. Two devices bootstrap trust with **card setup** (FFI roles `card_host`/`card_join`): a rotating PIN authenticates a short-lived connection, the cards cross it, and the user confirms the same key fingerprint on both screens before either is stored — card setup never carries clipboard content. After that either side hosts a clipboard session (`start`) and the other joins the peer it picks from the trusted list (`join`)
- strict no backward compatibility, legacy codes, or changelogs at all
- make changes on the sibling project ../duocb (the Rust core + FFI used by this app) if needed, use instructions on ../duocb/CLAUDE.md or ../duocb/CLAUDE.local.md for starting e2e test on desktop side for the opposite party
- **there is no "hub" FFI role.** The hub is pure local state — the trusted-device list is read from this app's own storage, nothing is broadcast and nothing is discovered — so no FFI handle exists while it is on screen. At most one handle runs at a time, and only for a session: `start`, `join`, `card_host` or `card_join` (SessionController)
- the signaling channel (`lan_then_nostr` default / `lan_only` / `nostr_only`) is the desktop's launch-fixed `--lan-only`/`--nostr-only`. iOS has no CLI, so it is a Settings picker read when a session starts; it governs card setup and clipboard sessions alike, and **both devices must be set to a channel they share** (unlike the old quick-pair PINs, the channel is not encoded in the code)
- the Rust artifact (libduocb.xcframework) is delivered via a local Swift package `Packages/Duocb/Package.swift` (referenced by local path in project.yml); its binary target downloads the pinned release zip by URL+checksum (SPM auto-exposes the embedded duocb.h to the bridging header, so no vendor/ dir and no HEADER_SEARCH_PATHS). Bump to a new release with `scripts/bump-xcframework.sh <tag>`. For FFI dev against a local Rust build, run `./build-ios.sh` in ../duocb then set `DUOCB_LOCAL_XCFRAMEWORK=1` for both `xcodegen generate` and `xcodebuild` — SPM forbids binary paths outside the package root, so the sibling's dist/ios is reached via the committed symlink `Packages/Duocb/local/libduocb.xcframework`
- minimum iOS 17 (SwiftUI + @Observable; no WebView, no Network Extension, no background modes — v1 is foreground-first)
- regenerate the project from project.yml after file additions/renames (`xcodegen generate`)
- persistence splits by sensitivity, not by convenience: the application private key and the permanent 8-char suffix live in the Keychain (`Keychain.swift` → `IdentityStore`, `SuffixStore`, both `…AfterFirstUnlockThisDeviceOnly`); the device name, this device's signed self-card and the trusted peers' cards live in a JSON file in Application Support (`ConfigStore.swift`, mirroring the desktop's config.rs field-for-field under the same snake_case names). Cards are public by design — a card is the thing you hand out — so the Keychain buys them nothing. Commit points: the key the moment it is generated/imported, the name and its freshly minted self-card the moment the name is confirmed, a peer's card the moment its fingerprint is confirmed. Editing a field alone never persists. The suffix is minted once and survives an identity reset
- **trust is imported, never inferred.** A card arriving over card setup is verified as well-formed and correctly signed and nothing more; the PIN is ~35 bits and its rendezvous record is offline-attackable, so possession of the PIN must not be enough to become trusted. `SessionController.incomingCard` parks it for the fingerprint comparison and only `importIncomingCard()` writes it to the trusted list
- self-cards expire after 30 days and are re-minted at launch once inside the 7-day renewal window (`needs_renewal` from `duocb_identity_card_info`). A lapsed peer card cannot pair and renders in warning colour rather than vanishing — parsing is deliberately clock-free in the core

# iOS vs the desktop core

Exactly one thing is compiled out of duocb-core on iOS: **iroh's own mDNS address lookup**, which opens multicast sockets in-process and needs Apple's restricted multicast entitlement. Regular mDNS is not lost — `lan/dnssd.rs` has an iOS backend driving the system mDNSResponder daemon over `dns_sd.h`, which does the multicast on the app's behalf.

Two consequences:

- `Info.plist` must list **both** Bonjour service types: `_duocb-pin._udp` (card setup) and `_duocb-host._udp` (the pairwise hosting record a clipboard session is found through — LAN-first, nostr as fallback). Dropping either compiles, links and launches, and then the LAN path silently never resolves. `ci/ci.sh`'s `unsigned` job and `.github/workflows/unsigned-ios.yml` both assert on this.
- A LAN-only dial never resolves a bare node id on iOS, because that lookup is gone. It works because both LAN rendezvous backends return the host's direct socket addresses alongside the node id. See `EndpointReadiness::LanDirect` in ../duocb.

# Build and test

This checkout lives on Linux; the build host is the `macvm` ssh alias (macOS + Xcode).

- `scripts/mac-ci.sh [jobs…]` — rsyncs this tree **and** ../duocb to `macvm:~/codes/staging-area/{duocb-ios,duocb}`, then runs `ci/ci.sh` there over ssh. Both land as siblings so the committed relative symlink `Packages/Duocb/local/libduocb.xcframework -> ../../../../duocb/dist/ios/…` still resolves. Build outputs (cargo `target/`, duocb `dist/`, this repo's `build/`) are excluded from the sync, which is what keeps the remote Rust build incremental — do not remove those excludes.
- `ci/ci.sh` jobs: `simulator`, `smoke` (boots a sim, launches, asserts it survives 5s — the only check that proves the Rust core actually loads), `unsigned` (Release archive + bundle/plist assertions), `device` (signed slice), `ffi` (rebuild ../duocb for iOS and link against it — the only job that compiles the `cfg(target_os = "ios")` core code at all).
- `--local` makes every job link ../duocb's working-tree build instead of the pinned release. **Required whenever the FFI has changed but no release carries it yet** — otherwise the Swift compiles against the pinned release's older duocb.h. e.g. `scripts/mac-ci.sh --local simulator smoke`.
- the `device` job cannot run over ssh: codesign needs a private key from the login keychain, which is locked in an ssh session (the bare symptom is `errSecInternalComponent`). `ci/ci.sh` fails fast with the unlock commands; they need the account password, so run that job from a GUI session on the Mac.
- direct verify command, if you are already on the Mac: `xcodebuild -project Duocb.xcodeproj -scheme DuocbApp -destination 'platform=iOS Simulator,name=iPhone 17' ARCHS=arm64 build` — libduocb.xcframework is arm64-only, so a generic `-sdk iphonesimulator` destination picks x86_64 and fails to link.
